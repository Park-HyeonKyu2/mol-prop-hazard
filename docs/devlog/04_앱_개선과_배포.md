# 04. 데모 개선과 배포

3편에서 만든 Streamlit 데모를 다른 사람이 써볼 수 있게 화면을 다듬고, Streamlit Community Cloud에 배포했다. 그 과정에서 모델 비교 결과의 재현성 문제도 하나 확인했다.

## 1. 입력 화면 개선

### 입력 방식

추천 후보 수, 녹는점·끓는점 허용 오차는 처음에 슬라이더로 만들었는데, 정확한 값을 맞추기 불편해서 `st.number_input`(직접 입력 + 증감 버튼)으로 바꿨다.

유사도 가중치(`alpha`, 0~3 사이 실수)는 숫자만 봐서는 무엇을 조절하는지 알기 어려웠다. 그래서 숫자 대신 의미가 드러나는 선택지로 바꿨다.

```python
ALPHA_OPTIONS = {
    "구조만 보기 (분자 모양만 비교)": 0.0,
    "구조 + 크기·극성·용해도 약간 반영": 0.5,
    "구조 + 크기·극성·용해도 균형있게 반영 (기본)": 1.0,
    "구조 + 크기·극성·용해도 많이 반영": 2.0,
}
alpha_label = st.selectbox("유사도 판단 기준", list(ALPHA_OPTIONS.keys()), index=2)
alpha = ALPHA_OPTIONS[alpha_label]
```

### SMILES 자동완성과 session_state 오류

SMILES를 직접 입력할 때, 입력한 문자열이 포함된 화합물을 데이터셋(14,008개)에서 찾아 버튼으로 보여주고 클릭하면 입력창에 채워지게 했다. 처음에는 버튼 클릭을 확인한 뒤 바로 `session_state`를 바꿨다.

```python
if cols[i % 4].button(label, key=f"suggest_{row['InChIKey']}"):
    st.session_state["smiles_input"] = row["SMILES"]
    st.rerun()
```

클릭하면 `StreamlitAPIException: st.session_state.smiles_input cannot be modified after the widget with key smiles_input is instantiated`가 발생했다. Streamlit은 같은 실행 안에서 이미 화면에 그려진 위젯의 값을 바꾸는 것을 막는데, 입력창이 버튼보다 먼저 그려졌기 때문이다. `st.rerun()`을 붙여도 값을 대입하는 시점에 바로 오류가 난다.

`on_click` 콜백으로 바꿔서 해결했다. 콜백은 다음 실행이 시작되기 전에 먼저 호출되므로, 입력창이 다시 그려지기 전에 값을 바꿀 수 있다.

```python
def _fill_smiles(value):
    st.session_state["smiles_input"] = value

cols[i % 4].button(label, key=f"suggest_{row['InChIKey']}",
                   on_click=_fill_smiles, args=(row["SMILES"],))
```

### 가격 필터

가격 데이터(44개)를 InChIKey 기준으로 데이터셋에 붙이고, "가격 정보 있는 후보만 보기" 옵션을 추가했다. 비스페놀 A로 확인해보면 가격이 있는 물질이 적어서 유사도는 0.03~0.16 수준으로 낮아진다. 가격 데이터가 부족하다는 한계가 화면에서도 그대로 드러나는 부분이다.

## 2. 배포 (Streamlit Community Cloud)

로컬(`localhost:8501`)에서만 돌던 앱을 누구나 접속할 수 있게 Streamlit Community Cloud에 배포했다. 이 서비스는 GitHub 저장소를 연결해서 배포하는데, 유해성 모델 파일(`tox21_models.joblib`)이 91MB로 GitHub의 파일당 제한(100MB)에 가까웠다. 큰 파일은 Git LFS로 관리하도록 설정했다.

```bash
git lfs install
git lfs track "models/tox21_models.joblib"
git add .gitattributes
```

앱이 사용하는 데이터와 모델 파일만 저장소에 포함하고, 라이브러리 버전은 `requirements.txt`에 고정했다.

## 3. 모델 비교 결과를 다시 돌렸더니 달랐다

2편의 모델 비교(fingerprint만 사용)를 같은 코드로 다시 실행했다. 회귀는 이전과 같이 HistGradientBoosting과 LightGBM이 가장 높았지만, 분류에서는 RandomForest가 12개 태스크 중 11개에서 앞섰다. 처음에는 10개였다.

코드는 `random_state=42`로 고정돼 있어서 같은 환경에서는 몇 번을 실행해도 같은 결과가 나온다. 차이가 생긴 태스크인 NR-ER-LBD를 보면 LogisticRegression 0.7936, RandomForest 0.7902로 차이가 0.003에 불과했다. 처음 실행한 뒤 scikit-learn, XGBoost, LightGBM 버전이 바뀌었는데, 이 정도로 근소한 차이는 버전 변화만으로도 순위가 뒤집힐 수 있다.

여기서 정리한 점은 두 가지다.

- 태스크별 1위 개수처럼 근소한 차이에 민감한 지표보다, 평균 AUC처럼 안정적인 지표로 결과를 설명하는 게 맞다. 평균 AUC 기준으로는 RandomForest(0.825)가 여전히 가장 높았다.
- 재현성을 위해 라이브러리 버전을 고정해야 한다. 배포용 `requirements.txt`에 버전을 명시한 것도 같은 이유다.

배포된 모델은 이미 서술자를 추가한 상태에서 학습과 튜닝을 거친 것이라 그대로 두었다.

## 정리

화면을 다듬고 배포까지 마쳐서, 링크만 있으면 누구나 SMILES를 입력해 물성·유해성 예측과 대체 후보를 확인할 수 있게 됐다. 프로젝트 전체의 한계점은 3편에 정리했다.
