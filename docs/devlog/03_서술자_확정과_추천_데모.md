# 03. 서술자 선정과 추천 데모

지난 글에서 가격 데이터 44개를 확보하고 데모를 만들 수 있겠다고 판단했다. 이번 글은 예측 모델에 넣을 서술자를 체계적으로 고르고, 최종 모델과 통합 데이터셋을 만든 뒤 Streamlit 추천 데모를 완성하기까지의 기록이다.

## 1. 서술자 개수를 정하는 기준 (녹는점)

2일차에는 서술자 6개를 직접 골라서 넣었다. 이번에는 RDKit이 계산하는 서술자 217개 전체를 후보로 두고, 녹는점 예측에 실제로 도움이 되는 것을 데이터로 고르기로 했다.

방법은 permutation importance다. 학습된 모델에서 서술자 하나의 값을 무작위로 섞었을 때 성능이 얼마나 떨어지는지로 중요도를 매기고, 상위 N개만 fingerprint에 붙여서 N에 따른 성능 변화(elbow curve)를 봤다.

### 첫 버전의 데이터 누수

처음 짠 코드는 중요도 계산과 성능 평가를 같은 test 데이터로 했다. 결과를 보니 서술자를 217개 다 넣었을 때가 100개일 때보다 낮게 나왔는데, 중요도를 test로 고른 뒤 같은 test로 평가했으니 test에 유리한 서술자가 뽑힌 것이다. 결과가 부풀려진 상태라 그대로 쓸 수 없었다.

그래서 5-fold 교차검증으로 바꿨다. 각 fold의 train으로만 모델을 학습하고 중요도를 계산한 뒤, 그 fold의 test에서만 평가했다.

```python
for train_idx, test_idx in KFold(n_splits=5, shuffle=True, random_state=42).split(mp_fp):
    # 1) train으로만 모델을 학습하고 중요도 계산 (test는 사용하지 않음)
    full_model.fit(X_full_train, y_train)
    importance_df = permutation_importance_train_only(full_model, X_full_train, y_train, FP_DIM, desc_names)

    # 2) 상위 N개 서술자만 붙여서 이 fold의 test로 평가
    for n in N_CANDIDATES:
        top_names = importance_df.head(n)["descriptor"].tolist()
        ...
```

| 서술자 수 N | R² (5-fold 평균) |
|---|---|
| 0 (fingerprint만) | 0.6466 |
| 10 | 0.7443 |
| 20 | 0.7524 |
| 40 | 0.7623 |
| 60 | 0.7637 |
| 217 | 0.7640 |

수정하고 나니 217개를 다 넣어도 성능이 떨어지지 않았고, N=40에서 얻을 수 있는 성능 향상의 약 99%에 도달했다. 그 이후는 fold 간 편차(표준편차 약 0.01)보다 작은 차이라서 N=40으로 정했다.

### Ipc 서술자 문제

학습 중 `ValueError: Input X contains infinity or a value too large for dtype('float32')`가 발생했다. 원인은 `Ipc` 서술자였다. 분자가 커지면 값이 급격히 커지는데, 녹는점 데이터에서는 2.6×10³⁸로 float32 최댓값(약 3.4×10³⁸)에 근접했고 유해성 데이터에서는 1.2×10⁴¹로 범위를 넘었다. 처음에는 값을 잘라내는(clip) 방식으로 막았다가, Ipc를 빼도 성능에 차이가 없는 것을 확인하고 후보에서 아예 제외했다.

### 하이퍼파라미터 튜닝과 비교 방법

녹는점 모델(HistGradientBoosting)을 `RandomizedSearchCV`로 튜닝했다. 960개 조합 중 30개를 뽑아 5-fold로 평가하는 데 약 30분(1,832초)이 걸렸고, 결과는 R² 0.7498이었다. 기본값(0.7623)보다 낮아서 처음에는 튜닝이 오히려 나쁘다고 판단했다.

나중에 모델 파일을 정리하면서 다시 확인해보니, 두 점수는 서로 다른 분할에서 나온 값이었다. `RandomizedSearchCV(cv=5)`는 회귀 문제에서 데이터를 섞지 않고 순서대로 5등분하고, 기본값 점수는 elbow curve에서 데이터를 섞어 5등분한 결과였다. 같은 분할(섞은 5-fold)로 다시 비교한 결과는 다음과 같다.

| 모델 | R² (5-fold 평균 ± 표준편차) |
|---|---|
| 기본값 | 0.7623 ± 0.014 |
| 튜닝 | 0.7689 ± 0.010 |

튜닝이 0.007 높지만 fold 간 편차 안의 차이이고, 튜닝 파라미터는 같은 데이터로 고른 것이라 점수가 약간 유리하게 나온다. 30분을 들인 것에 비해 의미 있는 개선이 없어서 더 단순한 기본값을 유지했다. 모델끼리 비교할 때는 반드시 같은 분할을 써야 한다는 걸 이 과정에서 배웠다.

## 2. 끓는점과 유해성에 맞는 서술자 따로 고르기

녹는점 기준으로 뽑은 상위 40개를 끓는점과 유해성 모델에도 그대로 쓰고 있었다는 걸 뒤늦게 발견했다. 물성마다 중요한 서술자가 다를 수 있으니 각각 다시 선정했다. 방법은 1장과 같고, 유해성은 12개 태스크별 중요도 순위를 평균 내서 정했다.

**끓는점 (단일 test split 기준)**

| N | R² |
|---|---|
| 0 (fingerprint만) | 0.7213 |
| 40 | 0.9302 |
| 60~217 | 0.928~0.929 |

**유해성 (12개 태스크 평균 AUC)**

| N | 평균 AUC |
|---|---|
| 0 | 0.8251 |
| 40 | 0.8514 |
| 60~217 | 0.847~0.851 |

둘 다 N=40 근처에서 성능이 더 오르지 않아 N=40으로 정했다. 녹는점의 상위 40개와 겹치는 서술자(TPSA, MolLogP 계열)도 있었지만 다른 것도 꽤 섞여 있어서, 물성별로 따로 고른 의미가 있었다. 다만 끓는점과 유해성은 시간 문제로 녹는점처럼 5-fold 교차검증까지는 하지 못했다.

## 3. 유해성 모델 튜닝

2일차 비교에서 RandomForest가 10개 태스크, LightGBM이 2개 태스크(NR-ER-LBD, SR-MMP)에서 앞섰다. 녹는점 튜닝에서 30분을 들이고도 의미 있는 개선이 없었던 만큼, 12개를 전부 튜닝하지 않고 LightGBM이 앞선 2개 태스크만 가볍게 튜닝했다.

```python
lgbm_param_dist = {

}

for task in ["NR-ER-LBD", "SR-MMP"]:

    )
    search.fit(X, y)
    # 기본값보다 나을 때만 튜닝 결과를 채택
```

| 태스크 | 기본값 | 튜닝 (n_iter=20) | 튜닝 (n_iter=50, 파라미터 8종) |

탐색 범위를 넓히면 조금 더 올랐지만 시간은 3~4배 걸렸다. 개선 폭이 줄어드는 구간이라 판단하고 n_iter=50 결과에서 멈췄다.

끓는점은 녹는점과 같은 이유로 기본값 HistGradientBoosting을 5-fold 교차검증으로 확인한 뒤 채택했다. 유해성은 RandomForest 10개와 튜닝한 LightGBM 2개를 합쳐 하나의 파일로 저장했다.

```python
tox21_models = {**rf_models, **lgbm_tuned}  # 10 + 2 = 12개 태스크
```

데모용 데이터셋은 처음에는 가격이 있는 44개로 만들려 했지만, 녹는점(7,037), 끓는점(4,795), 유해성(7,831) 데이터셋을 InChIKey 기준으로 합친 **14,008개** 전체로 범위를 넓혔다. 실측값이 있으면 그대로 쓰고, 없으면 저장한 모델로 예측해서 채운 뒤 `_source` 컬럼에 measured/predicted를 기록했다.

이 과정에서 `ValueError: The truth value of a Series is ambiguous`가 발생했다. 유해성 데이터셋에 InChIKey가 같은 행이 2쌍 있었던 게 원인이었다. 호변이성질체라 SMILES는 달라도 InChIKey는 같게 계산되는 경우다. `drop_duplicates(subset="InChIKey")`로 처리했다.

## 5. 추천 데모 (Streamlit)

추천 기준은 "구조가 비슷하면서 유해성이 더 낮은 물질"이다.

### 유사도에 물성 정보 반영

fingerprint의 코사인 유사도만 쓰면 구조 패턴만 비교하게 돼서, 크기나 극성이 전혀 다른 물질도 비슷하다고 나올 수 있다. 그래서 대체 가능성과 관련이 깊은 서술자 6개(분자량, LogP, TPSA, 수소결합 공여체·수용체 수, 회전 가능 결합 수)를 `StandardScaler`로 정규화해 fingerprint 뒤에 붙였다.

```python
query_vec = np.concatenate([fp, sim_desc_scaled * alpha])
master_vecs = np.hstack([fps, sim_desc_scaled_all * alpha])
sims = cosine_similarity(query_vec.reshape(1, -1), master_vecs)[0]
```

`alpha`는 구조와 물성 중 어느 쪽에 비중을 둘지 정하는 가중치로, 화면에서 직접 조절할 수 있게 했다.

### 필터 조건 버그

유해성 12개 태스크를 평균 하나로만 비교하면, 특정 태스크 하나만 위험하고 나머지가 낮은 물질이 통과할 수 있다. 그래서 태스크별로 "모두 입력 물질보다 낮아야 함" 조건을 추가했는데, 비스페놀 A로 테스트하니 후보가 항상 0개였다.

비스페놀 A는 측정값이 0인 태스크가 여러 개 있었고, 0보다 작은 값은 없으니 `<` 조건을 만족하는 후보가 나올 수 없었다. 조건을 파레토 우위(어느 태스크에서도 더 나쁘지 않고, 하나 이상에서 더 낮음)로 바꿨다.

```python
# 수정 전: 측정값이 0인 태스크가 있으면 항상 0개
mask &= (candidates[t] < result["hazard_probs"][t]).values

# 수정 후
not_worse &= (candidates[t] <= result["hazard_probs"][t]).values
better_any |= (candidates[t] < result["hazard_probs"][t]).values
candidates = candidates[not_worse & better_any]
```

수정 후 비스페놀 A(유해성 점수 0.357)는 후보 3,879개가 나왔다. 벤젠은 12개 라벨이 모두 0이라 더 낮은 후보가 없어 0개가 나오는데, 이건 의도한 동작이다.

## 한계점

**데이터**

- Tox21은 특정 어세이 12개(핵수용체 7종, 스트레스 반응 5종)만 다룬다. 발암성처럼 더 넓은 의미의 유해성은 포함하지 않는다. 벤젠은 12개 라벨이 모두 음성이지만 알려진 발암물질이다. 이 시스템의 "유해성 점수 0"은 안전하다는 뜻이 아니다.
- 유해성 라벨의 양성 비율이 2.9~16.2%로 낮다. 가중치로 보정했지만 양성 예측의 신뢰도는 상대적으로 낮다.
- 가격 데이터는 44개뿐이다. 대체 물질 간 비용 비교는 사실상 할 수 없는 수준이다.

**모델과 방법론**

- 녹는점은 결정 구조의 영향을 받아서, 2차원 구조 정보(fingerprint)로는 예측에 한계가 있다.
- 끓는점과 유해성의 서술자 선정은 녹는점과 달리 단일 split으로만 확인했다.
- 유해성 12개 태스크 중 10개는 서술자를 추가한 뒤 모델 비교를 다시 하지 않았다.
- 통합 데이터셋에서 실측값과 예측값을 `_source`로 구분은 했지만, 추천 로직에서는 둘을 같은 신뢰도로 취급한다.

**추천 로직**

- 유사도 계산용 서술자 6개는 예측용 서술자처럼 데이터로 검증해서 고른 게 아니라, 대체 가능성과 관련 있다고 판단해 고른 것이다.
- 구조와 물성이 비슷해도 실제로 대체할 수 있다는 보장은 없다. 구매 가능성, 규제, 용도 적합성은 반영하지 않았다.

## 마무리

데이터 정제부터 예측 모델, 14,008개 통합 데이터셋, 추천 데모까지 하나의 파이프라인을 직접 만들었다.

RDKit은 처음에 `mol` 객체가 무엇인지부터 찾아봐야 했는데, 지금은 SMILES에서 fingerprint, 서술자, InChIKey를 필요에 맞게 계산할 수 있다. Ipc 값이 float32 범위를 넘는 문제나 호변이성질체 때문에 InChIKey가 중복되는 문제는 실제 데이터로 작업하면서 처음 알게 됐다.

모델링에서는 9개 회귀 모델과 4개 분류 모델을 비교하고, 서술자 개수를 교차검증으로 정하고, 튜닝 결과를 기본값과 비교해 채택 여부를 정하는 과정을 직접 해봤다. 특히 서술자 선정 코드에서 데이터 누수를 발견하고 고친 경험, 서로 다른 교차검증 분할로 점수를 비교해 잘못된 결론을 냈다가 바로잡은 경험, 논리적으로 맞아 보이는 필터 조건이 실제 데이터에서는 항상 0개를 반환했던 경험이 기억에 남는다. 결과 숫자만큼 그 숫자를 의심하고 검증하는 과정이 중요하다는 걸 배웠다.

위에 적은 한계가 많아 아직 실사용 수준은 아니지만, 구조 하나로 물성과 유해성을 예측하고 대체 후보를 찾는 흐름을 처음부터 끝까지 만들어본 것에 의미가 있었다. 다음 글에서는 데모 화면을 다듬고 배포한 과정을 정리했다.
